# Maple Insight Data Studio Specification

## 1. 문서 목적

이 문서는 `apps/electron`에서 제공할 게임 데이터 관리 데스크톱 애플리케이션의
제품 요구사항과 시스템 제약을 정의한다.

이 문서는 **무엇을 구현해야 하는지**를 다룬다. 구현 순서와 일정은 `ROADMAP.md`,
현재 작업 단위는 `GOAL.md`, 검증 결과는 `REVIEW.md`에서 관리한다.

## 2. 제품 개요

Maple Insight Data Studio는 게임 데이터 원본을 수집하고 버전별로 검증, 비교, 편집한
뒤 데이터베이스와 TypeScript 데이터 패키지에 반영하기 위한 로컬 관리자 도구다.

핵심 처리 흐름은 다음과 같다.

```text
원본 파일 선택
  -> 작업 버전 지정
  -> 형식 변환 및 구조 검증
  -> 기존 버전과 차이 비교
  -> 사용자 검토 및 수정
  -> dry-run
  -> 사용자 승인
  -> DB 반영
  -> 타입 및 정적 데이터 생성
```

## 3. 목표

- CSV와 JSON 기반 게임 데이터를 하나의 작업 흐름에서 관리한다.
- 데이터 변경을 게임 버전 단위로 추적한다.
- 원본과 변환 결과의 차이를 사용자가 반영 전에 확인할 수 있게 한다.
- 장비, 직업, 스킬 등 도메인 데이터를 안전하게 추가, 수정, 삭제한다.
- DB 반영과 타입 생성을 재현 가능한 작업으로 만든다.
- 불명확한 데이터 분류에는 Jev를 보조적으로 사용하되 최종 결정권은 코드와 사용자에게 둔다.
- renderer, 파일 시스템, DB, 외부 API 사이에 명확한 보안 경계를 유지한다.

## 4. 비목표

초기 버전에서는 다음 기능을 제공하지 않는다.

- 일반 사용자를 위한 게임 정보 조회 기능
- 실시간 서비스 운영 및 배포 자동화
- 여러 관리자의 동시 편집
- 원격 협업과 역할 기반 접근 제어
- Jev 판단만으로 수행하는 자동 DB 반영
- 게임 클라이언트 파일의 직접 수정
- 이미지, 오디오, 비디오 데이터 분석

## 5. 사용자

### 데이터 관리자

프로젝트 개발자가 로컬 환경에서 사용한다.

- 새 게임 버전의 원본 파일을 가져온다.
- 변경 내용을 이전 버전과 비교한다.
- 정규화 결과를 검토하고 수정한다.
- DB 반영과 코드 생성을 명시적으로 승인한다.
- 실패한 작업의 로그를 확인하고 다시 실행한다.

## 6. 용어

| 용어        | 정의                                                                  |
| ----------- | --------------------------------------------------------------------- |
| 현재 버전   | 조회, 편집, 반영 작업의 대상이 되는 게임 데이터 버전                  |
| 비교 버전   | 현재 버전과 차이를 계산할 기준 버전                                   |
| 원본 데이터 | 외부에서 수집한 변경하지 않은 CSV 또는 JSON 파일                      |
| 작업본      | 원본을 파싱하고 정규화한 뒤 사용자가 검토하는 데이터                  |
| 데이터 묶음 | 하나의 게임 버전을 구성하는 장비, 직업, 스킬 등 관련 파일 집합        |
| dry-run     | DB를 변경하지 않고 예상 변경과 오류를 계산하는 작업                   |
| publish     | 승인된 작업본을 DB에 트랜잭션으로 반영하는 작업                       |
| ready 버전  | 필수 적재와 검증을 완료하여 조회 가능한 버전                          |
| Jev         | 제한된 후보에 대한 의미 기반 판단을 제공하는 TypeSafe System One 모델 |

## 7. 우선순위 표기

- `MUST`: 제품의 안전성이나 핵심 흐름에 필수
- `SHOULD`: 일반적인 운영을 위해 필요하지만 단계적으로 구현 가능
- `MAY`: 핵심 흐름 이후 선택적으로 구현

## 8. 기능 요구사항

### 8.1 애플리케이션 셸과 탐색

- `APP-001` `MUST`: 앱은 대시보드, 데이터 업로드, 버전 비교, 장비 데이터, 직업 데이터,
  DB 및 타입 작업 화면을 제공해야 한다.
- `APP-002` `MUST`: 선택된 화면과 현재 작업 버전을 항상 식별할 수 있어야 한다.
- `APP-003` `MUST`: 로딩, 성공, 경고, 실패 상태를 화면에서 구분해 표시해야 한다.
- `APP-004` `SHOULD`: 장시간 작업은 진행 단계와 처리 건수를 표시해야 한다.
- `APP-005` `MUST`: 세로 스크롤바 유무에 따라 전체 레이아웃이 수평으로 이동하지 않아야 한다.
- `APP-006` `SHOULD`: 현재 Electron 화면을 수동 또는 Playwright로 캡처하고 촬영 방식별 디렉터리에 저장할 수 있어야 한다.
- `APP-007` `SHOULD`: 다크·라이트 테마를 전환할 수 있고 선택값을 앱 재시작 후에도 유지해야 한다.
- `APP-008` `MUST`: 본문과 보조 텍스트는 각 테마 배경에서 읽을 수 있는 대비를 유지해야 한다.

### 8.2 데이터 버전 관리

- `VER-001` `MUST`: 버전은 `major.minor.patch` 형식으로 식별해야 한다.
- `VER-002` `MUST`: 앱은 DB에 등록된 `ready`, `importing` 버전을 선택 목록에 표시하고
  `failed` 버전은 제외해야 한다.
- `VER-003` `MUST`: 현재 버전 변경 시 모든 도메인 조회와 편집 컨텍스트가 함께 변경되어야 한다.
- `VER-004` `MUST`: 비교 버전은 버전 비교 화면의 기준으로 사용해야 한다.
- `VER-005` `SHOULD`: 두 개 이상의 버전이 있을 때 현재 버전과 비교 버전은 달라야 한다.
- `VER-006` `MUST`: 버전 적재 상태는 최소 `importing`, `ready`, `failed`를 지원해야 한다.
- `VER-007` `MUST`: 필수 데이터가 모두 검증되기 전에는 버전을 `ready`로 전환하지 않아야 한다.
- `VER-008` `SHOULD`: 버전별 생성 시각, 완료 시각, 마지막 변경 시각을 표시해야 한다.
- `VER-009` `SHOULD`: 버전 삭제 전 참조 데이터와 삭제 범위를 표시하고 별도 승인을 받아야 한다.
- `VER-010` `MUST`: patch `100~299`는 test, `300~499`는 production 환경으로 자동 분류해야 한다.
- `VER-011` `MUST`: 게임사 업데이트 날짜와 시스템 등록 시각을 별도 필드로 관리해야 한다.

### 8.3 파일 가져오기

- `IMP-001` `MUST`: 사용자는 OS native dialog로 버전 데이터 폴더를 선택할 수 있어야 한다.
- `IMP-002` `MUST`: renderer는 임의의 로컬 경로를 직접 읽을 수 없어야 한다.
- `IMP-003` `MUST`: 원본 파일은 수정하거나 덮어쓰지 않아야 한다.
- `IMP-004` `MUST`: 폴더명, CSV 파일 목록, 전체 크기, 수정 시각을 선택 결과로 표시해야 한다.
- `IMP-005` `MUST`: 파일은 명시적인 대상 버전에 연결되어야 한다.
- `IMP-006` `MUST`: 한 버전에 속하는 여러 CSV 파일을 하나의 가져오기 세션으로 묶어야 한다.
- `IMP-007` `SHOULD`: 같은 버전과 파일의 중복 적재 여부를 감지해야 한다.
- `IMP-008` `SHOULD`: 파일 해시를 기록하여 동일한 원본을 식별할 수 있어야 한다.
- `IMP-009` `MUST`: 지원하지 않는 확장자와 빈 파일을 검증 단계 전에 거부해야 한다.
- `IMP-010` `MUST`: 선택한 폴더 아래의 CSV 파일을 재귀 탐색하되 심볼릭 링크는 따라가지 않아야 한다.
- `IMP-011` `MUST`: 검증된 원본과 변환 결과를 `data/<environment>/<version>/{csv,json}` 구조로 원자적으로 반영해야 한다.
- `IMP-012` `MUST`: 표준 데이터 디렉터리 반영과 함께 버전을 `importing` 상태로 등록해야 한다.
- `IMP-013` `MUST`: 변환 성공 후 버전 선택 목록을 갱신하고 새 `importing` 버전을 현재 작업
  버전으로 선택해야 한다.

### 8.4 CSV 및 JSON 변환

- `CNV-001` `MUST`: CSV 입력을 내부 표준 JSON 구조로 변환할 수 있어야 한다.
- `CNV-002` `MUST`: JSON 입력은 파싱 가능 여부와 최상위 구조를 검증해야 한다.
- `CNV-003` `MUST`: 변환 결과는 원본과 분리된 작업 위치에 저장해야 한다.
- `CNV-004` `MUST`: 문자 인코딩, 헤더 중복, 열 개수 불일치, 잘못된 따옴표를 오류로 보고해야 한다.
- `CNV-005` `SHOULD`: 숫자처럼 보이는 ID의 앞자리 `0`을 보존해야 한다.
- `CNV-006` `MUST`: 변환 과정은 동일한 입력에 대해 동일한 결과를 생성해야 한다.
- `CNV-007` `SHOULD`: 변환 전후 레코드 수와 누락된 레코드 수를 요약해야 한다.

### 8.5 검증과 정규화

- `VAL-001` `MUST`: 공통 형식 검증과 도메인별 검증을 분리해야 한다.
- `VAL-002` `MUST`: 오류는 파일, 레코드, 필드, 원인 정보를 포함해야 한다.
- `VAL-003` `MUST`: 오류와 경고를 구분해야 한다.
- `VAL-004` `MUST`: 오류가 남아 있는 작업본은 publish할 수 없어야 한다.
- `VAL-005` `SHOULD`: 경고는 사용자가 확인하거나 예외 사유를 기록한 뒤 진행할 수 있어야 한다.
- `VAL-006` `SHOULD`: 정규화 전 값과 정규화 후 값을 함께 검토할 수 있어야 한다.
- `VAL-007` `MUST`: 결정론적으로 검증 가능한 값은 Jev가 아니라 코드로 검증해야 한다.

### 8.6 버전 비교

- `DIF-001` `MUST`: 현재 버전과 비교 버전 사이의 추가, 수정, 삭제 항목을 계산해야 한다.
- `DIF-002` `MUST`: 도메인별 안정적인 식별자를 기준으로 항목을 대응시켜야 한다.
- `DIF-003` `MUST`: 수정 항목은 필드 단위 이전 값과 이후 값을 표시해야 한다.
- `DIF-004` `SHOULD`: 도메인, 변경 종류, 검색어로 결과를 필터링할 수 있어야 한다.
- `DIF-005` `SHOULD`: 변경 요약과 전체 상세 결과를 함께 제공해야 한다.
- `DIF-006` `MUST`: 정렬 순서만 바뀐 데이터와 실제 값 변경을 구분해야 한다.
- `DIF-007` `MAY`: 비교 결과를 JSON 또는 Markdown 보고서로 내보낼 수 있다.

### 8.7 장비 데이터 관리

- `EQP-001` `MUST`: 현재 버전의 장비를 검색하고 상세 정보를 조회할 수 있어야 한다.
- `EQP-002` `MUST`: 장비를 추가, 수정, 삭제할 수 있어야 한다.
- `EQP-003` `MUST`: 장비명, 정규화 이름, 카테고리, 부위, 직업군, 요구 레벨 등 필수 필드를 검증해야 한다.
- `EQP-004` `MUST`: 잠재옵션 관련 데이터도 버전 컨텍스트 안에서 관리해야 한다.
- `EQP-005` `MUST`: 같은 버전 안에서 고유해야 하는 필드의 중복을 차단해야 한다.
- `EQP-006` `SHOULD`: 수정 전후 값을 작업 이력으로 확인할 수 있어야 한다.
- `EQP-007` `MUST`: 삭제는 즉시 DB에 반영하지 않고 작업본의 변경으로 기록해야 한다.

### 8.8 직업 데이터 관리

- `CLS-001` `MUST`: 현재 버전의 직업과 전직 정보를 검색하고 조회할 수 있어야 한다.
- `CLS-002` `MUST`: 직업 코드, 직업명, 계열, 소속, 전직 차수를 관리할 수 있어야 한다.
- `CLS-003` `MUST`: 직업 코드의 앞자리 `0`과 문자열 표현을 보존해야 한다.
- `CLS-004` `MUST`: 1.5차와 2.5차처럼 정수가 아닌 전직 단계를 표현할 수 있어야 한다.
- `CLS-005` `MUST`: 직업 추가, 수정, 삭제 시 관련 스킬과 참조 관계를 검증해야 한다.
- `CLS-006` `SHOULD`: 직업 계보와 그룹별 보기 기능을 제공해야 한다.

### 8.9 스킬 및 기타 도메인

- `SKL-001` `SHOULD`: 버전별 직업 스킬과 공용 스킬 데이터를 가져오고 조회할 수 있어야 한다.
- `SKL-002` `SHOULD`: source skill, linked skill, internal skill 관계를 보존해야 한다.
- `SKL-003` `SHOULD`: 5차 및 6차 코어의 연동 레벨 구조를 표현할 수 있어야 한다.
- `DOM-001` `MAY`: 몬스터, 보스, 심볼 등 다른 도메인을 같은 버전 작업 흐름에 추가할 수 있다.
- `DOM-002` `MUST`: 새 도메인을 추가할 때 기존 도메인의 처리 코드를 조건문으로 과도하게 확장하지 않아야 한다.

### 8.10 Jev 보조 분류

- `JEV-001` `MUST`: Jev SDK와 API 키는 Electron main process에서만 사용해야 한다.
- `JEV-002` `MUST`: renderer에는 API 키와 TypeSafe 클라이언트를 노출하지 않아야 한다.
- `JEV-003` `MUST`: 사용자가 명시적으로 요청한 경우에만 파일 분류 API를 호출해야 한다.
- `JEV-004` `MUST`: Jev에는 필요한 최소한의 텍스트만 전송해야 한다.
- `JEV-005` `MUST`: 파일 유형 분류는 `equipment`, `skill`, `class`, `monster`, `unknown`을 지원해야 한다.
- `JEV-006` `MUST`: 선택 결과와 함께 confidence, 확률 분포, 모델, 토큰 사용량을 보존해야 한다.
- `JEV-007` `MUST`: 낮은 confidence와 `unknown` 결과는 사용자 검토로 보내야 한다.
- `JEV-008` `MUST`: Jev 실패가 파일 선택이나 수동 분류 기능을 차단하지 않아야 한다.
- `JEV-009` `MUST`: Jev 판단만으로 DB 쓰기, 삭제, 타입 생성을 실행하지 않아야 한다.
- `JEV-010` `SHOULD`: 질문과 임계값은 한곳에서 관리하여 리뷰와 평가가 가능해야 한다.

세부 사용 원칙은 루트의 `JEV_GUIDE.md`를 따른다.

### 8.11 DB dry-run과 반영

- `DB-001` `MUST`: 실제 DB 반영 전에 dry-run을 실행해야 한다.
- `DB-002` `MUST`: dry-run은 예상 추가, 수정, 삭제 수와 실패 원인을 제공해야 한다.
- `DB-003` `MUST`: 사용자의 명시적 승인 없이는 publish를 실행하지 않아야 한다.
- `DB-004` `MUST`: 하나의 버전 publish는 가능한 한 단일 트랜잭션으로 처리해야 한다.
- `DB-005` `MUST`: publish 실패 시 부분 반영을 롤백하고 버전 상태를 `failed`로 기록해야 한다.
- `DB-006` `MUST`: 성공한 publish만 버전 상태를 `ready`로 변경해야 한다.
- `DB-007` `SHOULD`: 재시도 가능한 오류와 데이터 수정이 필요한 오류를 구분해야 한다.
- `DB-008` `MUST`: renderer는 Prisma나 DB 연결을 직접 사용하지 않아야 한다.

### 8.12 타입 및 정적 데이터 생성

- `GEN-001` `MUST`: DB에 반영된 ready 버전을 기준으로 타입과 정적 데이터를 생성해야 한다.
- `GEN-002` `MUST`: 생성 명령, 대상 버전, 결과 경로를 실행 전에 표시해야 한다.
- `GEN-003` `MUST`: 생성 결과를 Git diff로 검토하기 전 자동 커밋하지 않아야 한다.
- `GEN-004` `MUST`: 생성 실패가 DB 데이터를 되돌렸다고 오인하게 표시되어서는 안 된다.
- `GEN-005` `SHOULD`: 생성된 파일 수, 변경 파일 수, 오류를 요약해야 한다.
- `GEN-006` `SHOULD`: 데이터 적재와 생성 작업의 의존 순서를 명시적으로 실행해야 한다.

### 8.13 작업 이력과 복구

- `LOG-001` `MUST`: 가져오기, 검증, dry-run, publish, 생성 작업의 시작과 결과를 기록해야 한다.
- `LOG-002` `MUST`: 로그에 API 키, DB 비밀번호 등 비밀값을 기록하지 않아야 한다.
- `LOG-003` `SHOULD`: 실패 작업을 동일한 입력과 설정으로 재실행할 수 있어야 한다.
- `LOG-004` `SHOULD`: 작업 취소 시 현재 단계와 정리 결과를 표시해야 한다.
- `LOG-005` `MAY`: 이전 작업 결과와 diff 보고서를 앱에서 다시 열 수 있다.

## 9. 아키텍처 요구사항

### 9.1 프로세스 경계

```text
Renderer
  -> Preload API
  -> IPC Handler
  -> Main Process Service
  -> File System / Database / External API
```

- `ARC-001` `MUST`: renderer는 Node.js, 파일 시스템, DB에 직접 접근하지 않아야 한다.
- `ARC-002` `MUST`: `contextIsolation`을 활성화하고 `nodeIntegration`을 비활성화해야 한다.
- `ARC-003` `MUST`: preload는 필요한 기능만 명시적으로 노출해야 한다.
- `ARC-004` `MUST`: IPC 입력은 main process에서 런타임 검증해야 한다.
- `ARC-005` `MUST`: 파일 경로는 native dialog에서 승인한 범위 안에서만 사용해야 한다.
- `ARC-006` `SHOULD`: 파일, DB, Jev, 생성기 기능은 main process 서비스로 분리해야 한다.
- `ARC-007` `MUST`: 외부 URL은 Electron 창 안에서 임의로 열지 않아야 한다.

### 9.2 데이터 소유권

- `OWN-001` `MUST`: 원본 파일은 불변 입력으로 취급해야 한다.
- `OWN-002` `MUST`: DB는 서비스에서 사용하는 버전 데이터의 최종 소유자가 되어야 한다.
- `OWN-003` `MUST`: 패키지의 생성 파일은 DB 또는 승인된 작업본에서 재생성 가능해야 한다.
- `OWN-004` `MUST`: 앱 UI 상태를 DB의 영구 데이터와 혼동하지 않아야 한다.

## 10. 보안 요구사항

- `SEC-001` `MUST`: `DATABASE_URL`, `TYPESAFE_API_KEY` 등 비밀값을 renderer에 전달하지 않아야 한다.
- `SEC-002` `MUST`: 비밀값을 소스 코드, 로그, Git 추적 파일에 저장하지 않아야 한다.
- `SEC-003` `MUST`: 모든 DB 변경 작업은 대상 버전과 변경 범위를 사용자에게 표시해야 한다.
- `SEC-004` `MUST`: 삭제와 publish는 일반 탐색 동작과 분리된 명시적 승인 절차를 가져야 한다.
- `SEC-005` `SHOULD`: 외부 API로 전송될 데이터의 크기와 내용을 제한해야 한다.
- `SEC-006` `SHOULD`: 패키징된 앱에서 개발자 도구와 새 창 열기 동작을 제한해야 한다.

## 11. 비기능 요구사항

### 11.1 성능

- `NFR-PERF-001`: 대용량 파일은 가능한 한 스트리밍 또는 청크 단위로 처리해야 한다.
- `NFR-PERF-002`: 긴 작업이 renderer의 UI 스레드를 차단하지 않아야 한다.
- `NFR-PERF-003`: 목록은 데이터 증가에 대비해 페이지네이션 또는 가상화를 지원할 수 있어야 한다.

### 11.2 안정성

- `NFR-REL-001`: 외부 API나 DB 연결 실패가 앱 프로세스 전체 종료로 이어지지 않아야 한다.
- `NFR-REL-002`: 실패한 작업은 원본과 기존 ready 버전을 손상시키지 않아야 한다.
- `NFR-REL-003`: 동일 입력을 다시 처리해도 중복 데이터가 생기지 않아야 한다.

### 11.3 사용성

- `NFR-UX-001`: 사용자는 항상 현재 버전과 비교 버전을 확인할 수 있어야 한다.
- `NFR-UX-002`: 실행 버튼에는 대상, 영향, 현재 상태가 드러나야 한다.
- `NFR-UX-003`: 오류 메시지는 실패 원인과 다음 조치를 포함해야 한다.
- `NFR-UX-004`: 색상만으로 상태를 구분하지 않아야 한다.

### 11.4 호환성

- `NFR-COMP-001`: Windows 실행 파일 배포를 우선 지원해야 한다.
- `NFR-COMP-002`: Linux/WSL 개발 환경에서 typecheck, lint, build가 가능해야 한다.
- `NFR-COMP-003`: 플랫폼별 경로 구분자를 직접 조합하지 않고 Node.js path API를 사용해야 한다.

### 11.5 관측 가능성

- `NFR-OBS-001`: 각 작업은 상태, 시작 시각, 종료 시각, 처리 건수, 오류를 보고해야 한다.
- `NFR-OBS-002`: 외부 API 결과는 모델과 사용량 정보를 함께 기록할 수 있어야 한다.
- `NFR-OBS-003`: 사용자 표시 로그와 개발 진단 로그를 구분해야 한다.

## 13. 완료 기준

초기 제품의 핵심 흐름은 다음 조건을 모두 만족할 때 완료로 본다.

1. 새 버전의 CSV/JSON 데이터 묶음을 선택할 수 있다.
2. 원본을 변경하지 않고 작업본을 생성한다.
3. 형식 및 도메인 검증 결과를 확인할 수 있다.
4. 이전 ready 버전과 추가, 수정, 삭제 차이를 확인할 수 있다.
5. 장비와 직업 작업본을 편집할 수 있다.
6. dry-run 결과를 확인하고 명시적으로 승인할 수 있다.
7. 실패 시 부분 반영 없이 복구되며 원인을 확인할 수 있다.
8. 성공 시 버전이 ready가 되고 해당 버전으로 데이터를 조회할 수 있다.
9. 타입과 정적 데이터 생성 결과를 Git diff로 검토할 수 있다.
10. renderer 번들에 DB 또는 TypeSafe 인증 정보가 포함되지 않는다.

## 14. 현재 구현 상태

이 절은 요구사항이 아니라 문서 작성 시점의 구현 스냅샷이다.

### 구현됨

- Electron, React, Vite, TailwindCSS 기반 애플리케이션 셸
- 대시보드와 주요 화면 탐색
- DB의 ready/importing 버전 목록 조회와 failed 버전 제외
- 현재 버전과 비교 버전 선택 상태
- OS native dialog 기반 버전 데이터 폴더 선택
- 폴더 아래 CSV 재귀 탐색과 파일 목록, 크기, 수정 시각 표시
- 여러 CSV의 단일 세션 스트림 변환과 파일별 NDJSON 작업본
- `data/<environment>/<version>/{csv,json}` 저장과 importing 버전 등록
- 변환 성공 후 버전 목록 갱신과 새 버전 선택
- 다크·라이트 테마와 전체 화면 스크린샷
- main/preload/renderer 보안 경계의 기본 구성
- main/preload의 Jev 파일 유형 분류 서비스 (폴더 가져오기 UI에서는 미사용)
- `GameDataVersion` 및 버전 연관 DB 구조
- 버전 묶음 seed의 importing/ready/failed 처리 기반

### 부분 구현

- 버전 비교 화면과 도메인 관리 화면은 UI 골격만 존재
- DB 및 타입 작업 화면은 작업 항목만 표시
- 데이터 업로드의 실제 DB 반영과 도메인 검증은 연결되지 않음
- 작업 상태는 일부 정적 표시이며 실제 실행 상태와 연결되지 않음

### 미구현

- 파일 및 도메인별 validation
- 버전 diff 계산과 상세 표시
- 장비 및 직업 CRUD 작업본
- dry-run, 승인, publish UI
- 타입 및 정적 데이터 생성 실행
- 작업 이력, 취소, 재시도 및 복구
- Jev confidence 기반 수동 검토 정책
