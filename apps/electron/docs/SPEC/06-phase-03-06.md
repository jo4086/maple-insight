## 16. Phase 3~6 추가 요구사항 (계획)

기존 §8~§13 요구사항과 완료 기준을 유지한다. 아래 번호는 기존 ID를 재정의하지 않는다. 기술적 저장 형식·schema mapping은 [아키텍처](../ARCHITECTURE.md), 구현·검증 상태는 [GOAL](../GOAL/README.md)와 [REVIEW](../REVIEW.md)를 따른다.

<a id="spec-edit-workbench"></a>
### 16.1 데이터 경계와 편집 작업본

원본 CSV·변환 JSON은 불변 입력이며 validation workspace, `data/diff` 산출물, 편집 작업본, DB publish는 서로 다른 소유 경계다.

- `VAL-008` `MUST`: validation issue는 파일·레코드·필드·severity·코드·원인과 안정된 issue ID를 기록해야 한다.
- `VAL-009` `MUST`: 경고 확인·예외 사유는 report와 validation workspace manifest에 저장하고 재실행 후 복원해야 한다.
- `VAL-010` `MUST`: 검증 실행·진행·취소와 경고 갱신은 main/preload IPC 경계를 거쳐야 한다. 실제 Electron IPC 검증은 §12.8의 별도 미완료 조건이다.
- `LOG-006` `MUST`: validation 실행은 식별자·입력 hash·시작·종료·상태·처리 건수·issue 요약을 기록하되 비밀값과 이미지 원본은 기록하지 않아야 한다.
- `SEC-007` `MUST`: 관리 데이터 경로는 승인된 데이터 루트 안에서만 해석하고 상위 경로·절대 경로·심볼릭 링크 우회를 거부해야 한다.
- `SEC-008` `MUST`: 외부 이미지 전송은 탐색·미리보기와 분리된 명시적 동의 뒤에만 허용하고 renderer·로그에 이미지 원본을 노출하지 않아야 한다.

- `EWB-001` `MUST`: edit workbench는 `data/.edit-workbenches/<environment>/<version>/<changeSetId>/`에 저장한다. `changeSetId`는 생성 뒤 바뀌지 않는 UUID다.
- `EWB-002` `MUST`: manifest는 `schemaVersion`, `changeSetId`, environment, version, validation workspace manifest hash, raw input hash, 상태, 생성·수정 시각, 생성자 로컬 식별자, 부모 change-set ID를 가진다.
- `EWB-003` `MUST`: job metadata, skill metadata, skill type, damage modifier, equipment draft, equipment evidence, weapon catalog 변경은 각 레코드에 안정된 record ID, domain, operation, 원시 identity, before hash, after 값, revision, 검토 상태를 저장한다.
- `EWB-004` `MUST`: evidence candidate 레코드는 불변 `evidenceId`, 대상 `equipmentDraftId`, target field, proposal value, confidence 값·scale·산출 제공자/모델 버전, candidate 상태, reviewer·결정 시각, 원본 파일 hash, 명시적 동의 시각·범위, 보관 만료 시각, 외부 전송 여부를 저장한다. accepted candidate는 확정 equipment revision 또는 record ID를 연결한다. 기본값은 이미지 경로·바이트를 저장하지 않는 것이다.
- `EWB-005` `MUST`: validation workspace 입력 hash가 바뀌면 기존 change-set을 재사용하지 않고 새 change-set을 만든다. 이전 change-set은 읽기 전용 superseded 상태로 남긴다.
- `EWB-006` `MUST`: draft, dry-run-ready, approved, publishing, published, failed, discarded, superseded 상태 전이와 허용 주체를 main process가 검증한다.
- `EWB-007` `MUST`: dry-run은 manifest와 정렬된 모든 레코드의 canonical hash를 입력으로 하며, hash가 바뀌면 승인과 dry-run 결과를 무효화한다.
- `EWB-008` `MUST`: 실패·취소 publish는 workbench와 evidence candidate metadata를 보존하고 DB transaction만 롤백한다. discarded는 명시적 사용자 동의 뒤에만 삭제한다.
- `EWB-009` `MUST`: candidate 상태는 `proposed`, `accepted`, `rejected`, `superseded`다. `proposed`는 확정 equipment 값과 분리하며, `accepted`·`rejected`는 reviewer와 결정 시각을 가져야 한다. 수동 편집이 이미 accepted candidate의 목표 필드를 바꾸면 candidate는 `superseded`가 된다.

<a id="spec-phase-03"></a>
### 16.2 초기 다섯 공통 파일 비교

기존 `DIF-001`~`DIF-007`의 비교·필터·내보내기 요구는 유지한다. 장비 비교는 Phase 4 후속 확장이다. 기존 UI의 **비교 버전** 선택값은 기준 데이터인 `baseVersion`, **현재 버전** 선택값은 변경된 대상인 산출물의 `compareVersion`에 대응한다. 산출물 필드명과 UI 선택기 명칭은 동일한 뜻이 아니다.

- `DIF-008` `MUST`: 사용자는 기준 버전, 대상 버전, 공통 파일명 하나를 선택한다.
- `DIF-009` `MUST`: 초기 대상은 `ms_job.json`, `ms_skill.json`, `ms_skillH.json`, `ms_skillCommon.json`, `ms_skillLevel.json`이다.
- `DIF-010` `MUST`: `ms_skillPVPCommon.json`은 이 비교 기능에서 제외한다.
- `DIF-011` `MUST`: 결과를 `data/diff/<baseVersion>_to_<compareVersion>/<filename>`에 저장한다.
- `DIF-012` `MUST`: 산출물 최상위에는 `baseVersion`, `compareVersion`, `add`, `modify`, `delete`를 둔다.
- `DIF-013` `MUST`: UI는 추가·수정 패널과 삭제 패널을 나누고, 수정은 필드별 before/after를 표시한다.
- `DIF-014` `MUST`: identity를 파일별로 명시한다. job은 `jobID`, skill과 skillH는 `skillID`, common은 `(skillID, commonName)`, level은 `(skillID, level)`이다.
- `DIF-015` `MUST`: identity 누락·중복, 한쪽 버전의 파일 누락은 오류로 보고한다. 빈 결과나 삭제로 추정하지 않는다.
- `DIF-016` `MUST`: 배열 순서 변경은 수정이 아니며 identity 값 변경은 delete와 add다.

<a id="spec-phase-04-jobs"></a>
### 16.3 직업과 스킬 보강

기존 `CLS-001`~`CLS-006`, `SKL-001`~`SKL-003`(source/linked/internal 및 5·6차 코어 관계 포함)을 유지한다. 스킬 페이지는 계획이며 구현되지 않았다.

- `CLS-007` `MUST`: raw `jobID`·`jobName`을 보존하고 새 job에 영어 이름, 무기 유형, 한손/양손, 무기 상수·속도, 보조 무기, 주·부 스탯, 계열·소속을 수동 보강할 수 있다.
- `CLS-008` `MUST`: `jobID`는 문자열 identity이며 앞자리 0을 보존한다.
- `SKL-004` `MUST`: 새 `jobID`에 스킬을 연결하고 링크, 1~4차, 하이퍼, 패시브, 5차, 6차 분류와 active/passive/buff/summon 유형을 관리한다.
- `SKL-005` `MUST`: `ms_skill.json`, `ms_skillH.json`, `ms_skillCommon.json`, `ms_skillLevel.json`을 skillID로 연결해 기본 정보, 툴팁, 공통 값·수식, 레벨 설명을 표시한다.
- `SKL-006` `MUST`: PVP common은 이 스킬 연결 범위에서 제외한다.
- `SKL-007` `MUST`: Formula Grammar v1은 `+`, `-`, `*`, `/`, 괄호, ASCII 정수 리터럴, 단일 변수 `x`·`X`, 그리고 단항 함수 `u(expr)`·`log7(expr)`만 파싱한다. 공백은 token 사이에서만 허용한다. 우선순위는 괄호, 단항 부호, `*`·`/`, `+`·`-` 순서다. 예: `10+3*x`, `3+u(x/2)`, `2*(x-6)*log7(x)`.
- `SKL-008` `MUST`: Formula Grammar v1은 최대 256 UTF-8 bytes, 128 tokens, 괄호·AST depth 16, 함수 호출 depth 8을 허용한다. 변수 `x`·`X`는 외부 레코드 참조가 아닌 현재 skill level의 symbolic parameter다. v1에는 다른 identifier 기반 참조 namespace가 없다. parser는 syntax·limit만 검사하며 값을 평가하거나 type-check하지 않는다.
- `SKL-009` `MUST`: v1 밖의 identifier, 함수, 소수·지수 리터럴, 문자열, placeholder, 배열, 비교·논리·대입, property access, escape sequence, Unicode 연산자와 한도 초과는 `unsupported` 또는 `invalid` 원문 상태로 기록한다. 원문·파일·skillID·commonName을 표시하고 실행·자동 수정·publish 차단 근거로 사용하지 않는다. 검토자는 별도 수동 확인 상태를 기록할 수 있다.
- `SKL-010` `MUST`: `ms_skillH.json`과 `ms_skillLevel.json`의 tooltip·설명은 Formula Grammar 대상이 아닌 원문 텍스트다. raw `#c공격키#`와 `#c7레벨 : ...`은 값 참조가 아닌 서식 마크업이다. 스캔은 원문을 보존하며 왼쪽에서 오른쪽으로 처리한다. `#c` 바로 다음 문자가 숫자 또는 비 ASCII 문자면 서식 span으로 우선 분류한다. 종료 `#`가 있으면 거기까지, 없으면 줄 끝까지 span으로 둔다. span 내부는 placeholder 검색에서 제외한다. 그 외의 `#[A-Za-z][A-Za-z0-9_]*`만 값 placeholder 후보로 취급하고 같은 `skillID`의 `ms_skillCommon.json`에서 이름이 정확히 같은 `commonName`을 찾는다. `#cooltime`처럼 `#c` 뒤에 ASCII 문자가 오면 이 후보 규칙을 적용한다. 없는 값만 `unresolved placeholder`로 표시한다. 인식하지 못한 마크업은 원문·위치를 표시하되 참조 오류로 단정하지 않으며, 어떤 문자열도 치환·실행하지 않는다.
- `SKL-011` `MUST`: 범용 `eval` 또는 동등한 동적 실행으로 수식·tooltip·placeholder를 평가하지 않는다.
- `SKL-012` `MUST`: 스킬 페이지의 계획된 `스킬 유형` 하위 탭은 현 앱 탐색에 이미 있다고 표시하지 않는다.

### 16.4 스킬 유형과 피해 규칙

- `RULE-001` `MUST`: 유형과 피해 보정자는 versioned 작업본에서 관리한다.
- `RULE-002` `MUST`: 같은 damage 그룹의 보정자는 합산한다.
- `RULE-003` `MUST`: 서로 다른 critical 그룹의 결과는 곱연산한다.
- `RULE-004` `MUST`: boss-only, normal-only, debuff, 빈 조건을 지원한다. 빈 조건은 대상 조건과 독립적으로 적용 후보가 된다.
- `RULE-005` `MUST`: 적용성은 대상 조건, debuff 상태, 유형·그룹 순으로 판정한다.
- `RULE-006` `MUST`: boss-only와 normal-only 동시 지정, 알 수 없는 조건, 중복 규칙 ID를 거부한다.
- `RULE-007` `MUST`: boss, normal, debuff 유무, 빈 조건, 합산·곱연산, 상충 조건을 fixture로 검증한다.

<a id="spec-phase-04-equipment"></a>
### 16.5 장비 수동 입력과 스크린샷 후보

기존 `EQP-001`~`EQP-007`의 잠재옵션·이력·삭제 예약 요구는 유지한다. 장비 원본 API 없이 수동으로 입력하고 후보는 확정값과 분리한다.

- `EQP-008` `MUST`: 무기 유형은 versioned weapon type catalog의 안정 키로 선택한다.
- `EQP-009` `SHOULD`: 여러 스크린샷에서 후보 필드를 만들 수 있다.
- `EQP-010` `MUST`: candidate는 대상 equipment draft ID와 target field, 제안값, confidence 값·scale, 제공자/모델 버전, evidence ID를 표시한다. `proposed` candidate는 확정값이 아니며 사용자가 accepted 또는 rejected를 기록하기 전에는 publish 대상이 될 수 없다.
- `EQP-011` `MUST`: accepted candidate는 reviewer·결정 시각과 확정 equipment revision 또는 record ID를 연결한다. 수동 override는 새 revision을 만들고 이전 candidate를 superseded로 바꾼다.
- `EQP-012` `MUST`: 이미지 선택 전 명시적 동의, 로컬·외부 처리 여부, 보관 정책, 인식 한계를 표시한다. 동의 범위에는 처리 제공자와 만료 시각을 포함한다.
- `EQP-013` `MUST`: 동의 없는 외부 이미지 전송을 하지 않으며 원본 이미지를 기본 작업 이력·workbench·DB에 복사하지 않는다. 필요한 경우 사용자가 고른 관리 evidence 저장소에만 hash 검증 후 암호화 저장하고, 만료·discarded 시 삭제한다.

<a id="spec-phase-05"></a>
### 16.6 DB 반영과 생성 제약

현 `GameJob(version, jobId, jobName)`, raw 지향 `GameSkill` 계열, versioned `EquipmentItem`에 없는 metadata·rule은 Phase 5 migration 제안이다. nullable 확장, backfill, 읽기 전환, 제약 강화 순서를 적용한다.

- `DB-009` `MUST`: 직업·스킬 metadata, 스킬 유형·피해 규칙, 무기 catalog, 장비 draft·evidence, publish 승인·실행 이력을 승인된 change-set 원본 identity·record ID와 연결해야 한다.
- `DB-010` `MUST`: dry-run은 DB를 변경하지 않고 작업본 canonical hash·예상 변경·오류에 연결하며 hash 변경 시 기존 승인과 dry-run을 무효화해야 한다.
- `DB-011` `MUST`: 실패 publish는 작업본과 evidence metadata를 보존하고 DB transaction 변경만 롤백해야 한다. 생성 실패는 DB publish 롤백으로 표시하지 않아야 한다.

### 16.7 추가 수용 fixture (미검증)

1. 다섯 공통 파일 fixture는 identity별 add/modify/delete와 필드 before/after를 재현한다.
2. 중복·누락 identity와 누락 파일 fixture는 오류를 내고 산출물을 추정하지 않는다.
3. 새 raw job 보강과 skill 연결 fixture는 원본 JSON·문자열 ID를 변경하지 않는다.
4. 수식 fixture는 Formula Grammar v1의 `10+3*x`, `3+u(x/2)`, `2*(x-6)*log7(x)`를 parse-only로 통과시키고, 알 수 없는 identifier·함수, placeholder, 문자열, 비교·대입, 한도 초과를 실행 없이 `unsupported` 또는 `invalid`로 기록한다. tooltip fixture는 raw `#c공격키#`, 닫는 `#` 없는 `#c7레벨 : ...`을 서식으로 분류해 참조 오류를 만들지 않고, 같은 skill의 `commonName`이 존재하는 `#mpCon`은 후보로 확인하며, 없는 `#missingValue`만 `unresolved placeholder`와 원문 위치를 표시한다. `#cooltime`을 서식으로 삼지 않고 일반 값 후보로 분류한다.
5. 피해 규칙 fixture는 합산, distinct critical 곱, 네 조건과 상충 조건 거부를 확인한다.
6. 장비 후보 fixture는 같은 field의 충돌 후보, rejection, accepted 뒤 수동 override, 동의 만료, 동의 없는 외부 전송 거부를 확인한다. candidate가 accepted revision을 연결하기 전에는 DB publish 대상에 포함되지 않는다.
7. dry-run fixture는 DB 쓰기 없이 변경 요약을 만들고, 승인 해시 변경 뒤 publish를 거부한다.
8. edit workbench fixture는 hash 변경 시 새 change-set 생성·승인 무효화, failed publish 후 workbench 보존, discarded 명시 삭제를 확인한다.

Phase 2 `EL-G002`의 실제 native IPC, production 대용량 응답성, class 외 coverage는 아직 완료되지 않았다.
