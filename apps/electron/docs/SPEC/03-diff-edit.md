### 8.6 버전 비교

- `DIF-001` `MUST`: 현재 버전과 비교 버전 사이의 추가, 수정, 삭제 항목을 계산해야 한다.
- `DIF-002` `MUST`: 도메인별 안정적인 식별자를 기준으로 항목을 대응시켜야 한다.
- `DIF-003` `MUST`: 수정 항목은 필드 단위 이전 값과 이후 값을 표시해야 한다.
- `DIF-004` `SHOULD`: 도메인, 변경 종류, 검색어로 결과를 필터링할 수 있어야 한다.
- `DIF-005` `SHOULD`: 변경 요약과 전체 상세 결과를 함께 제공해야 한다.
- `DIF-006` `MUST`: 정렬 순서만 바뀐 데이터와 실제 값 변경을 구분해야 한다.
- `DIF-007` `MAY`: 비교 결과를 JSON 또는 Markdown 보고서로 내보낼 수 있다.
- `DIF-016` `MUST`: DB에 등록된 두 버전 중 관리 JSON이 없는 경우 파일 목록과 비교 실행에 유용한 누락 파일 설명을 표시한다. DB 목록에서 해당 버전을 제거하거나 빈 결과로 추정하지 않는다.
- `DIF-017` `MUST`: 파일 목록 조회의 loading과 error 상태는 React StrictMode effect cleanup 뒤에도 새 effect를 활성 상태로 복원한다. 취소된 이전 요청은 반영하지 않되 `파일 목록 조회 중` phantom loading 때문에 선택기·비교 버튼이 영구 비활성화되어서는 안 된다.
- `DIF-018` `MUST`: 원본 JSON·diff 결과 경로는 같은 승인 데이터 루트 안에서만 해석한다. DB 등록 목록은 이 파일 존재 검사와 독립적으로 유지한다.
- `DIF-019` `MUST`: 비교 선택기는 화면에서 `현재 버전 → DIFF → 기준 버전` 순서로 표시한다. 현재 버전은 변경 대상 `compareVersion`, 기준 버전은 `baseVersion`이며 비교 계산과 `data/diff/<baseVersion>_to_<compareVersion>/` 저장 의미는 변경하지 않는다.

> `DIF-020`~~`DIF-031`은 별도 개요·상세 화면 요청의 이력이다. [통합 비교 작업공간 요청](../REQUESTS/comparison-workspace.md)과 `DIF-032`~~`DIF-053`가 이를 대체하며, 아래 원문과 과거 검증 기록은 삭제하지 않는다.

- `DIF-020` `MUST` (대체됨): 비교 실행 결과는 요약을 빠르게 파악하는 개요와 전체 결과를 검토하는 상세 화면으로 분리한다.
- `DIF-021` `MUST` (대체됨): 개요는 추가·수정·삭제 카테고리별 건수를 표시하고, 선택한 카테고리의 레코드 하나만 전체 개요에서 한 번에 미리 보여준다. 카테고리를 전환해 미리보기 대상을 바꾸며 개요에는 페이지 이동을 제공하지 않는다.
- `DIF-022` `MUST` (대체됨): 상세 화면은 전체·추가·수정·삭제 카테고리, 검색과 페이지 이동을 제공한다. 추가·삭제 카드는 레코드 전체 JSON을, 수정 카드는 변경 필드별 전체 before/after 값을 잘림 없이 표시한다. 전체 diff 산출물을 한 번에 표시하는 동작은 제공하지 않는다.
- `DIF-023` `MUST` (대체됨): 상세 화면은 스크롤 중에도 검색·페이지 이동·저장 동작에 접근할 수 있어야 한다.
- `DIF-024` `MUST` (대체됨): 저장 완료 결과를 다시 열어 개요와 상세로 확인할 수 있어야 하며 빈 결과와 검색 결과 없음을 구분한다. 저장 결과 조회 실패와 일반 저장 실패는 오류를 표시하되 같은 입력 컨텍스트의 현재 결과는 재시도를 위해 유지할 수 있다.
- `DIF-025` `MUST` (대체됨): 버전·파일 선택 변경과 새 비교 시작은 이전 결과를 현재 결과처럼 남기지 않는다. 저장 요청에서 현재 입력과 결과의 hash 불일치가 확인되면 stale 결과를 무효화한다.
- `DIF-026` `MUST` (대체됨): 개요·상세·저장 결과는 모바일 폭에서도 선택기, 카테고리, 상세 검색·페이지 이동·고정 저장 동작과 카드의 전체 값에 접근할 수 있어야 한다.
- `DIF-027` `MUST` (대체됨): 비교 화면의 제목, 본문, label, 수치, JSON 표시는 기존 Electron 화면과 같은 타이포그래피 계층과 간격을 사용한다.
- `DIF-028` `MUST` (대체됨): 버전 관리의 하위 탐색에는 `리스트`, `비교`와 형제인 `상세 결과`를 항상 표시하고 활성화한다.
- `DIF-029` `MUST` (대체됨): `상세 결과` 직접 진입에 현재 비교 결과가 없으면 빈 상태와 정확히 `버전 비교로 이동`인 동작을 표시한다. 개요의 `전체 결과 자세히`와 `상세 결과`는 같은 수동 `View` 경로로 이동한다.
- `DIF-030` `MUST` (대체됨): 앱이 최신 비교 결과를 메모리에 보유하는 동안 개요와 `상세 결과`가 그 결과를 함께 사용한다. 비교 화면은 다른 화면으로 이동해도 mounted 상태를 유지하고, 버전·파일 선택 변경은 결과를 지운다. 앱 재시작 뒤에는 결과를 복원하지 않으며 디스크 영속 상태를 추가하지 않는다.
- `DIF-031` `MUST` (대체됨): `상세 결과` 진입과 최신 결과 공유에는 새 상태 관리 또는 routing dependency를 추가하지 않는다.

#### 통합 비교 작업공간

- `DIF-032` `MUST`: `/compare` 한 화면에서 전역 현재 버전을 사용하고, 기준 버전·파일 선택, 다섯 파일 실행 상태·요약, 선택 파일 결과 검토와 저장을 처리한다. 별도 개요·상세 화면 전환은 사용하지 않는다.
- `DIF-033` `MUST`: 현재 버전(`compareVersion`)과 기준 버전(`baseVersion`)을 한 번 선택해 `ms_job.json`, `ms_skill.json`, `ms_skillH.json`, `ms_skillCommon.json`, `ms_skillLevel.json`을 한 번의 동작으로 순차 비교·저장한다. 기존 파일별 compare/open/save IPC, identity, 비교 방향과 저장 경로를 유지하며 새 batch IPC를 추가하지 않는다.
- `DIF-034` `MUST` (2026-10-24 표시 방식 대체됨): 다섯 파일의 상태·건수를 동시에 나열한 고정 카드 목록은 사용하지 않는다. 파일 dropdown은 파일명만 표시하고 추가·수정·삭제 건수는 선택 파일에만 표시한다. 실패한 파일을 선택하면 오류 원인과 해당 파일의 동작을 개별 표시한다. 한 파일의 실패는 다른 파일 처리를 중단하거나 성공 결과를 지우지 않는다.
- `DIF-035` `MUST`: 비교에 성공한 파일만 저장한다. 같은 입력 hash의 유효한 기존 산출물은 덮어쓰기나 확인 없이 재사용하고, 비교 또는 저장에 실패한 파일에는 새 산출물이 있다고 표시하지 않으며 기존 산출물을 보존한다.
- `DIF-036` `MUST`: 기존 산출물의 입력 hash가 다르거나 산출물이 malformed이면 해당 파일에 교체 승인을 요구한다. 승인 전, 취소와 실패에는 기존 산출물을 보존하고 명시적으로 승인한 파일만 교체한다.
- `DIF-037` `MUST` (2026-10-24 일부 대체됨): 데스크톱의 세 panel과 독립 결과 스크롤 계약은 유지한다. 고정 파일 카드 목록과 하단 pager 요구는 `DIF-042`~`DIF-046`이 대체한다.
- `DIF-038` `MUST` (2026-10-24 field-row refinement, `DIF-050`~`DIF-053`으로 대체됨): 결과는 추가·수정·삭제 필터, 검색과 상단 페이지 이동을 제공한다. 추가·삭제는 기존과 같이 전체 JSON 레코드를 표시한다. 수정 레코드를 모든 파일에서 같은 카드 형식으로 변경 필드와 필드별 이전·이후 값만 표시한 계약은 과거 이력으로 유지한다. 강조와 표시는 원본 값을 바꾸지 않아야 한다.

> 최초 `DIF-038`의 전체 snapshot 기본 표시와 이를 대체한 `DIF-047`의 field-row 표시는 모두 과거 구현·검증 이력이다. 최신 screenshot refinement는 `DIF-050`~`DIF-053`이 정의하며 과거 요구사항과 검증 기록은 삭제하지 않는다.

- `DIF-039` `MUST`: 버전 변경과 새 전체 실행은 이전 결과를 현재 결과처럼 남기지 않는다. 비동기 비교·저장 응답은 버전·파일·입력 hash가 현재 작업과 일치할 때만 반영한다.
- `DIF-040` `MUST`: 기존 `/compare-results` 경로는 별도 결과 상태 복원이나 재비교 없이 `/compare`로 redirect한다.
- `DIF-041` `MUST`: 데스크톱과 모바일 폭에서 파일 상태·전환, 추가·삭제 전체 JSON, 수정 전후 JSON, 검색·페이지 이동, 재시도·저장·교체 확인에 접근할 수 있어야 하며 상태와 변경 강조를 색상만으로 구분하지 않는다. 수정 전후 JSON의 최신 responsive 배치는 `DIF-053`을 따른다.
- `DIF-042` `MUST`: 현재 버전(`compareVersion`) 선택은 전역 상단 selector 하나만 사용한다. 작업공간의 기준 버전(`baseVersion`)과 파일은 초기 미선택이며 파일 selector는 파일명만 표시하는 dropdown이다.
- `DIF-043` `MUST`: 유효한 기준 버전·파일 선택에 저장 결과가 있으면 자동으로 연다. 선택 변경 시 stale 결과, 변경 유형 필터, 검색어와 page를 초기화하고 이전 비동기 응답을 반영하지 않는다.
- `DIF-044` `MUST`: 선택한 기준 버전·파일의 저장 결과가 없으면 빈 상태를 유지하며 비교 또는 저장을 자동 실행하지 않는다.
- `DIF-045` `MUST`: 다섯 파일 순차 batch, 파일별 상태·오류·재시도와 충돌 승인 계약은 selector 배치 변경 뒤에도 유지한다.
- `DIF-046` `MUST`: 본문은 얇은 divider로 구분한 왼쪽·가운데·오른쪽 세 panel로 구성하고 가운데 결과 panel을 더 넓은 flexible grid column으로 둔다. 오른쪽 panel은 제목만 표시하고 내용은 비워 둔다. pager는 결과 상단에만 둔다.
- `DIF-047` `MUST` (`DIF-050`~`DIF-053`으로 대체됨): 모든 파일의 수정 레코드를 legacy·신규 diff 산출물의 선택적 전체 snapshot 유무와 무관하게 `DIF-038`의 동일한 변경 필드 카드로 표시한 field-row 계약은 과거 이력으로 유지한다.
- `DIF-048` `MUST`: 유효한 선택에 저장 결과를 자동으로 연 경우 성공 notice를 표시하지 않는다. 저장 결과 조회 실패와 다른 오류 표시는 유지한다.
- `DIF-049` `MUST`: `DIF-047`~`DIF-048`은 renderer 표시 계약만 변경한다. legacy·신규 diff 산출물의 저장 형식과 선택적 전체 snapshot, identity, 비교 알고리즘, 입력 hash 및 저장·충돌 정책은 변경하지 않는다.
- `DIF-050` `MUST`: `screenshots/manual/electron/electron-request-3.png`를 최신 표시 기준으로 삼는다. 모든 수정 카드는 `수정` label을 가진 얇은 outline의 단일 container 안에 이전·이후 JSON box 두 개를 나란히 표시하고, 변경된 값은 각 box에서 강조한다.
- `DIF-051` `MUST`: 저장 산출물에 전체 `before`·`after` snapshot이 있으면 이전·이후 JSON box에 변경되지 않은 필드를 포함한 전체 snapshot을 표시한다.
- `DIF-052` `MUST`: 전체 snapshot이 없는 legacy 산출물도 `DIF-050`과 같은 두 box 형상을 사용한다. 각 box에는 산출물에서 확인 가능한 최선의 identity와 변경 필드의 해당 시점 값만 표시하며, 사용할 수 없는 변경되지 않은 필드를 추정하거나 생성하지 않는다.
- `DIF-053` `MUST`: 좁은 폭에서는 이전·이후 JSON box를 세로로 쌓는다. `DIF-050`~`DIF-053`은 renderer 표시만 변경하며 비교 알고리즘, diff 저장 형식, 선택적 snapshot 계약, identity, 입력 hash 및 저장·충돌 정책은 변경하지 않는다.

### 8.7 장비 데이터 관리

- `EQP-001` `MUST`: 현재 버전의 장비를 검색하고 상세 정보를 조회할 수 있어야 한다.
- `EQP-002` `MUST`: 장비를 추가, 수정, 삭제할 수 있어야 한다.
- `EQP-003` `MUST`: 장비명, 정규화 이름, 카테고리, 부위, 직업군, 요구 레벨 등 필수 필드를 검증해야 한다.
- `EQP-004` `MUST`: 잠재옵션 관련 데이터도 버전 컨텍스트 안에서 관리해야 한다.
- `EQP-005` `MUST`: 같은 버전 안에서 고유해야 하는 필드의 중복을 차단해야 한다.

- `EQP-007` `MUST`: 삭제는 즉시 DB에 반영하지 않고 작업본의 변경으로 기록해야 한다.

### 8.8 직업 데이터 관리

- `CLS-001` `MUST`: 현재 버전의 직업과 전직 정보를 검색하고 조회할 수 있어야 한다.
- `CLS-002` `MUST`: 직업 코드, 직업명, 계열, 소속, 전직 차수를 관리할 수 있어야 한다.
- `CLS-003` `MUST`: raw `jobID`는 숫자 문자열 identity로 취급하고 앞자리 `0`과 문자열 표현을 보존해야 한다.
- `CLS-004` `MUST`: 1.5차와 2.5차처럼 정수가 아닌 전직 단계를 표현할 수 있어야 한다.
- `CLS-005` `MUST`: 직업 추가, 수정, 삭제 시 관련 스킬과 참조 관계를 검증해야 한다.
- `CLS-006` `SHOULD`: 직업 계보와 그룹별 보기 기능을 제공해야 한다.

### 8.9 스킬 및 기타 도메인

raw `commonValue`가 빈 문자열(`''`)이면 유효한 값이다. 필드 누락 또는 문자열이 아닌 값은 validation 오류이며, 어떤 경우에도 raw 값을 자동 수정하거나 삭제하지 않는다.

- `SKL-001` `SHOULD`: 버전별 직업 스킬과 공용 스킬 데이터를 가져오고 조회할 수 있어야 한다.
- `SKL-002` `SHOULD`: source skill, linked skill, internal skill 관계를 보존해야 한다.
- `SKL-003` `SHOULD`: 5차 및 6차 코어의 연동 레벨 구조를 표현할 수 있어야 한다.
- `DOM-001` `MAY`: 몬스터, 보스, 심볼 등 다른 도메인을 같은 버전 작업 흐름에 추가할 수 있다.
- `DOM-002` `MUST`: 새 도메인을 추가할 때 기존 도메인의 처리 코드를 조건문으로 과도하게 확장하지 않아야 한다.

### 8.10 Jev 보조 분류

- `JEV-001` `MUST`: Jev SDK와 API 키는 Electron main process에서만 사용해야 한다.
- `JEV-002` `MUST`: renderer에는 API 키와 TypeSafe 클라이언트를 노출하지 않아야 한다.
- `JEV-003` `MUST`: 사용자가 명시적으로 요청한 경우에만 파일 분류 API를 호출해야 한다.
- `JEV-004` `MUST`: Jev에는 필요한 최소한의 텍스트만 전송해야 한다.
- `JEV-005` `MUST`: 파일 유형 분류는 `equipment`, `skill`, `class`, `monster`, `unknown`을 지원해야 한다.
- `JEV-006` `MUST`: 선택 결과와 함께 confidence, 확률 분포, 모델, 토큰 사용량을 보존해야 한다.
- `JEV-007` `MUST`: 낮은 confidence와 `unknown` 결과는 사용자 검토로 보내야 한다.
- `JEV-008` `MUST`: Jev 실패가 파일 선택이나 수동 분류 기능을 차단하지 않아야 한다.
- `JEV-009` `MUST`: Jev 판단만으로 DB 쓰기, 삭제, 타입 생성을 실행하지 않아야 한다.
- `JEV-010` `SHOULD`: 질문과 임계값은 한곳에서 관리하여 리뷰와 평가가 가능해야 한다.

세부 사용 원칙은 루트의 `JEV_GUIDE.md`를 따른다.
