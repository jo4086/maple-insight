### 8.6 버전 비교

- `DIF-001` `MUST`: 현재 버전과 비교 버전 사이의 추가, 수정, 삭제 항목을 계산해야 한다.
- `DIF-002` `MUST`: 도메인별 안정적인 식별자를 기준으로 항목을 대응시켜야 한다.
- `DIF-003` `MUST`: 수정 항목은 필드 단위 이전 값과 이후 값을 표시해야 한다.
- `DIF-004` `SHOULD`: 도메인, 변경 종류, 검색어로 결과를 필터링할 수 있어야 한다.
- `DIF-005` `SHOULD`: 변경 요약과 전체 상세 결과를 함께 제공해야 한다.
- `DIF-006` `MUST`: 정렬 순서만 바뀐 데이터와 실제 값 변경을 구분해야 한다.
- `DIF-007` `MAY`: 비교 결과를 JSON 또는 Markdown 보고서로 내보낼 수 있다.
- `DIF-016` `MUST`: DB에 등록된 두 버전 중 관리 JSON이 없는 경우 파일 목록과 비교 실행에 유용한 누락 파일 설명을 표시한다. DB 목록에서 해당 버전을 제거하거나 빈 결과로 추정하지 않는다.
- `DIF-017` `MUST`: 파일 목록 조회의 loading과 error 상태는 React StrictMode effect cleanup 뒤에도 새 effect를 활성 상태로 복원한다. 취소된 이전 요청은 반영하지 않되 `파일 목록 조회 중` phantom loading 때문에 선택기·비교 버튼이 영구 비활성화되어서는 안 된다.
- `DIF-018` `MUST`: 원본 JSON·diff 결과 경로는 같은 승인 데이터 루트 안에서만 해석한다. DB 등록 목록은 이 파일 존재 검사와 독립적으로 유지한다.

### 8.7 장비 데이터 관리

- `EQP-001` `MUST`: 현재 버전의 장비를 검색하고 상세 정보를 조회할 수 있어야 한다.
- `EQP-002` `MUST`: 장비를 추가, 수정, 삭제할 수 있어야 한다.
- `EQP-003` `MUST`: 장비명, 정규화 이름, 카테고리, 부위, 직업군, 요구 레벨 등 필수 필드를 검증해야 한다.
- `EQP-004` `MUST`: 잠재옵션 관련 데이터도 버전 컨텍스트 안에서 관리해야 한다.
- `EQP-005` `MUST`: 같은 버전 안에서 고유해야 하는 필드의 중복을 차단해야 한다.
- `EQP-006` `SHOULD`: 수정 전후 값을 작업 이력으로 확인할 수 있어야 한다.
- `EQP-007` `MUST`: 삭제는 즉시 DB에 반영하지 않고 작업본의 변경으로 기록해야 한다.

### 8.8 직업 데이터 관리

- `CLS-001` `MUST`: 현재 버전의 직업과 전직 정보를 검색하고 조회할 수 있어야 한다.
- `CLS-002` `MUST`: 직업 코드, 직업명, 계열, 소속, 전직 차수를 관리할 수 있어야 한다.
- `CLS-003` `MUST`: raw `jobID`는 숫자 문자열 identity로 취급하고 앞자리 `0`과 문자열 표현을 보존해야 한다.
- `CLS-004` `MUST`: 1.5차와 2.5차처럼 정수가 아닌 전직 단계를 표현할 수 있어야 한다.
- `CLS-005` `MUST`: 직업 추가, 수정, 삭제 시 관련 스킬과 참조 관계를 검증해야 한다.
- `CLS-006` `SHOULD`: 직업 계보와 그룹별 보기 기능을 제공해야 한다.

### 8.9 스킬 및 기타 도메인

raw `commonValue`가 빈 문자열(`''`)이면 유효한 값이다. 필드 누락 또는 문자열이 아닌 값은 validation 오류이며, 어떤 경우에도 raw 값을 자동 수정하거나 삭제하지 않는다.

- `SKL-001` `SHOULD`: 버전별 직업 스킬과 공용 스킬 데이터를 가져오고 조회할 수 있어야 한다.
- `SKL-002` `SHOULD`: source skill, linked skill, internal skill 관계를 보존해야 한다.
- `SKL-003` `SHOULD`: 5차 및 6차 코어의 연동 레벨 구조를 표현할 수 있어야 한다.
- `DOM-001` `MAY`: 몬스터, 보스, 심볼 등 다른 도메인을 같은 버전 작업 흐름에 추가할 수 있다.
- `DOM-002` `MUST`: 새 도메인을 추가할 때 기존 도메인의 처리 코드를 조건문으로 과도하게 확장하지 않아야 한다.

### 8.10 Jev 보조 분류

- `JEV-001` `MUST`: Jev SDK와 API 키는 Electron main process에서만 사용해야 한다.
- `JEV-002` `MUST`: renderer에는 API 키와 TypeSafe 클라이언트를 노출하지 않아야 한다.
- `JEV-003` `MUST`: 사용자가 명시적으로 요청한 경우에만 파일 분류 API를 호출해야 한다.
- `JEV-004` `MUST`: Jev에는 필요한 최소한의 텍스트만 전송해야 한다.
- `JEV-005` `MUST`: 파일 유형 분류는 `equipment`, `skill`, `class`, `monster`, `unknown`을 지원해야 한다.
- `JEV-006` `MUST`: 선택 결과와 함께 confidence, 확률 분포, 모델, 토큰 사용량을 보존해야 한다.
- `JEV-007` `MUST`: 낮은 confidence와 `unknown` 결과는 사용자 검토로 보내야 한다.
- `JEV-008` `MUST`: Jev 실패가 파일 선택이나 수동 분류 기능을 차단하지 않아야 한다.
- `JEV-009` `MUST`: Jev 판단만으로 DB 쓰기, 삭제, 타입 생성을 실행하지 않아야 한다.
- `JEV-010` `SHOULD`: 질문과 임계값은 한곳에서 관리하여 리뷰와 평가가 가능해야 한다.

세부 사용 원칙은 루트의 `JEV_GUIDE.md`를 따른다.
