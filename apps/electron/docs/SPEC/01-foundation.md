# Maple Insight Data Studio Specification

## 1. 문서 목적

이 문서는 `apps/electron`에서 제공할 게임 데이터 관리 데스크톱 애플리케이션의
제품 요구사항과 시스템 제약을 정의한다.

이 문서는 **무엇을 구현해야 하는지**를 다룬다. 구현 순서와 일정은 [ROADMAP](../ROADMAP.md),
현재 작업 단위는 [GOAL](../GOAL/README.md), 검증 결과는 [REVIEW](../REVIEW.md)에서 관리한다.

## 2. 제품 개요

Maple Insight Data Studio는 게임 데이터 원본을 수집하고 버전별로 검증, 비교, 편집한
뒤 데이터베이스와 TypeScript 데이터 패키지에 반영하기 위한 로컬 관리자 도구다.

핵심 처리 흐름은 다음과 같다.

```text
원본 파일 선택
  -> 작업 버전 지정
  -> 형식 변환 및 구조 검증
  -> 기존 버전과 차이 비교
  -> 사용자 검토 및 수정
  -> dry-run
  -> 사용자 승인
  -> DB 반영
  -> 타입 및 정적 데이터 생성
```

## 3. 목표

- CSV와 JSON 기반 게임 데이터를 하나의 작업 흐름에서 관리한다.
- 데이터 변경을 게임 버전 단위로 추적한다.
- 원본과 변환 결과의 차이를 사용자가 반영 전에 확인할 수 있게 한다.
- 장비, 직업, 스킬 등 도메인 데이터를 안전하게 추가, 수정, 삭제한다.
- DB 반영과 타입 생성을 재현 가능한 작업으로 만든다.
- 불명확한 데이터 분류에는 Jev를 보조적으로 사용하되 최종 결정권은 코드와 사용자에게 둔다.
- renderer, 파일 시스템, DB, 외부 API 사이에 명확한 보안 경계를 유지한다.

## 4. 비목표

초기 버전에서는 다음 기능을 제공하지 않는다.

- 일반 사용자를 위한 게임 정보 조회 기능
- 실시간 서비스 운영 및 배포 자동화
- 여러 관리자의 동시 편집
- 원격 협업과 역할 기반 접근 제어
- Jev 판단만으로 수행하는 자동 DB 반영
- 게임 클라이언트 파일의 직접 수정
- 범용 이미지, 오디오, 비디오 데이터 분석 (Phase 4의 장비 스크린샷 후보 입력·사용자 검토는 제한된 별도 흐름)

## 5. 사용자

### 데이터 관리자

프로젝트 개발자가 로컬 환경에서 사용한다.

- 새 게임 버전의 원본 파일을 가져온다.
- 변경 내용을 이전 버전과 비교한다.
- 정규화 결과를 검토하고 수정한다.
- DB 반영과 코드 생성을 명시적으로 승인한다.
- 실패한 작업의 로그를 확인하고 다시 실행한다.

## 6. 용어

| 용어        | 정의                                                                  |
| ----------- | --------------------------------------------------------------------- |
| 현재 버전   | 조회, 편집, 반영 작업의 대상이 되는 게임 데이터 버전                  |
| 비교 버전   | 현재 버전과 차이를 계산할 기준 버전                                   |
| 원본 데이터 | 외부에서 수집한 변경하지 않은 CSV 또는 JSON 파일                      |
| 작업본      | 원본을 파싱하고 정규화한 뒤 사용자가 검토하는 데이터                  |
| 데이터 묶음 | 하나의 게임 버전을 구성하는 장비, 직업, 스킬 등 관련 파일 집합        |
| dry-run     | DB를 변경하지 않고 예상 변경과 오류를 계산하는 작업                   |
| publish     | 승인된 작업본을 DB에 트랜잭션으로 반영하는 작업                       |
| ready 버전  | 필수 적재와 검증을 완료하여 조회 가능한 버전                          |
| Jev         | 제한된 후보에 대한 의미 기반 판단을 제공하는 TypeSafe System One 모델 |

## 7. 우선순위 표기

- `MUST`: 제품의 안전성이나 핵심 흐름에 필수
- `SHOULD`: 일반적인 운영을 위해 필요하지만 단계적으로 구현 가능
- `MAY`: 핵심 흐름 이후 선택적으로 구현

## 8. 기능 요구사항

### 8.1 애플리케이션 셸과 탐색

- `APP-001` `MUST`: 앱은 대시보드, 데이터 업로드, 버전 비교, 장비 데이터, 직업 데이터,
  DB 및 타입 작업 화면을 제공해야 한다.
- `APP-002` `MUST`: 선택된 화면과 현재 작업 버전을 항상 식별할 수 있어야 한다.
- `APP-003` `MUST`: 로딩, 성공, 경고, 실패 상태를 화면에서 구분해 표시해야 한다.
- `APP-004` `SHOULD`: 장시간 작업은 진행 단계와 처리 건수를 표시해야 한다.
- `APP-005` `MUST`: 세로 스크롤바 유무에 따라 전체 레이아웃이 수평으로 이동하지 않아야 한다.
- `APP-006` `SHOULD`: 현재 Electron 화면을 수동 또는 Playwright로 캡처하고 촬영 방식별 디렉터리에 저장할 수 있어야 한다.
- `APP-007` `SHOULD`: 다크·라이트 테마를 전환할 수 있고 선택값을 앱 재시작 후에도 유지해야 한다.
- `APP-008` `MUST`: 본문과 보조 텍스트는 각 테마 배경에서 읽을 수 있는 대비를 유지해야 한다.

### 8.2 데이터 버전 관리

- `VER-001` `MUST`: 버전은 `major.minor.patch` 형식으로 식별해야 한다.
- `VER-002` `MUST`: 앱은 DB에 등록된 `ready`, `importing` 버전을 선택 목록에 표시하고
  `failed` 버전은 제외해야 한다.
- `VER-003` `MUST`: 현재 버전 변경 시 모든 도메인 조회와 편집 컨텍스트가 함께 변경되어야 한다.
- `VER-004` `MUST`: 비교 버전은 버전 비교 화면의 기준으로 사용해야 한다.
- `VER-005` `SHOULD`: 두 개 이상의 버전이 있을 때 현재 버전과 비교 버전은 달라야 한다.
- `VER-006` `MUST`: 버전 적재 상태는 최소 `importing`, `ready`, `failed`를 지원해야 한다.
- `VER-007` `MUST`: 필수 데이터가 모두 검증되기 전에는 버전을 `ready`로 전환하지 않아야 한다.
- `VER-008` `SHOULD`: 버전별 생성 시각, 완료 시각, 마지막 변경 시각을 표시해야 한다.
- `VER-009` `SHOULD`: 버전 삭제 전 참조 데이터와 삭제 범위를 표시하고 별도 승인을 받아야 한다.
- `VER-010` `MUST`: patch `100~299`는 test, `300~499`는 production 환경으로 자동 분류해야 한다.
- `VER-011` `MUST`: 게임사 업데이트 날짜와 시스템 등록 시각을 별도 필드로 관리해야 한다.
