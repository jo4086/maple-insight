# Maple Insight Data Studio Roadmap

## 1. 문서 목적

이 문서는 `SPEC.md`의 요구사항을 구현 가능한 단계로 나누고 단계 간 의존 순서를 정의한다.

- 제품 요구사항의 기준: `SPEC.md`
- 현재 작업과 완료 조건: `GOAL.md`
- 구현 및 검증 결과: `REVIEW.md`

## 2. 상태 정의

| 상태    | 의미                                                |
| ------- | --------------------------------------------------- |
| 완료    | 구현과 검증이 끝났으며 다음 단계에서 사용할 수 있음 |
| 진행 중 | 현재 구현 또는 검증 중                              |
| 준비    | 선행 조건이 충족되어 다음 GOAL로 선택 가능          |
| 대기    | 선행 단계가 완료되어야 시작 가능                    |
| 보류    | 필요하지만 초기 제품 범위 이후에 진행               |

단계는 코드가 존재하는 것만으로 완료하지 않는다. 각 단계의 종료 조건과 검증 결과가
`REVIEW.md`에 기록되어야 완료로 변경한다.

## 3. 구현 원칙

1. 원본 파일은 항상 불변으로 유지한다.
2. renderer는 파일 시스템, DB, 외부 API에 직접 접근하지 않는다.
3. 입력, 변환, 검증, diff, publish를 서로 분리한다.
4. 가져오기 상태 메타데이터를 제외한 도메인 DB 데이터는 dry-run과 사용자 승인 전에 변경하지 않는다.
5. 결정론적 규칙은 코드로 처리하고 Jev는 의미 기반 판단에만 사용한다.
6. 새 단계는 이전 단계의 안정된 출력 계약을 입력으로 사용한다.
7. 기능 구현과 UI 표시를 같은 완료 조건으로 묶지 않는다.

## 4. 단계 의존성

```text
Phase 0: 애플리케이션 기반
  -> Phase 1: 파일 가져오기 및 변환
    -> Phase 2: 검증 및 작업본
      -> Phase 3: 버전 diff
        -> Phase 4: 도메인 편집
          -> Phase 5: DB dry-run 및 publish
            -> Phase 6: 타입 및 정적 데이터 생성
              -> Phase 7: 운영 안정화
```

Jev는 Phase 0에서 연결 기반을 마련하고, 각 단계에서 의미 기반 판단이 필요한 경우에만
보조 기능으로 확장한다.

## 5. Phase 0 - 애플리케이션 기반

**상태: 완료**

### 목표

Electron 앱의 보안 경계, 화면 구조, 버전 컨텍스트와 외부 서비스 연결 기반을 마련한다.

### 범위

- Electron, React, Vite, TailwindCSS 구성
- main, preload, renderer 프로세스 경계
- 공통 레이아웃과 화면 탐색
- DB ready/importing 버전 조회
- 현재 버전과 비교 버전 선택
- native file dialog
- Jev SDK와 파일 유형 분류

### 관련 요구사항

- `APP-001` ~ `APP-005`
- `VER-001` ~ `VER-006`
- `IMP-001` ~ `IMP-005`
- `JEV-001` ~ `JEV-006`
- `ARC-001` ~ `ARC-007`
- `SEC-001`, `SEC-002`, `SEC-005`

### 현재 상태

- 애플리케이션 셸과 주요 화면이 구현되어 있다.
- ready/importing 버전 목록과 현재/비교 버전 선택이 연결되어 있다.
- 버전 폴더를 native dialog로 선택하고 하위 CSV를 탐색할 수 있다.
- Jev 파일 유형 분류가 main process에 연결되어 있다.
- 테마 전환과 수동/Playwright 스크린샷 기반이 구현되어 있다.
- 실제 Jev 성공 호출과 Windows 패키징은 운영 검증으로 남아 있다.

### 종료 조건

- [x] Electron 앱의 typecheck, lint, production build 결과가 `REVIEW.md`에 기록되어 있다.
- [x] 파일 선택과 버전 조회의 정상 및 실패 경로를 검증했다.
- [x] renderer 번들에 DB 및 TypeSafe 비밀값이 포함되지 않음을 검증했다.
- [x] Jev 연결 실패가 파일 선택 기능을 차단하지 않음을 검증했다.
- [x] IPC 입력에 대한 런타임 검증 정책이 정리되어 있다.

## 6. Phase 1 - 파일 가져오기 및 변환

**상태: 완료**

### 목표

CSV와 JSON 원본을 안전하게 읽고 재현 가능한 내부 표준 데이터로 변환한다.

### 범위

- 가져오기 세션과 대상 버전 연결
- 버전 폴더 선택과 다중 CSV 세션
- CSV 파서와 JSON 파서
- 원본 메타데이터 및 해시
- 내부 표준 레코드 구조
- 작업 디렉터리와 변환 결과 관리
- 대용량 파일의 청크 또는 스트리밍 처리
- 변환 진행률과 취소

### 관련 요구사항

- `IMP-001` ~ `IMP-013`
- `CNV-001` ~ `CNV-007`
- `NFR-PERF-001`, `NFR-PERF-002`
- `NFR-REL-001` ~ `NFR-REL-003`

### 산출물

- 파일 입력 계약
- 변환 서비스와 결과 타입
- IPC 진행 상태 계약
- 업로드 화면의 변환 결과 요약
- CSV/JSON fixture 및 단위 테스트

### 종료 조건

- [x] CSV와 JSON fixture를 같은 내부 구조로 변환할 수 있다.
- [x] 원본 파일이 변경되지 않음을 테스트로 확인했다.
- [x] ID의 앞자리 `0`이 보존된다.
- [x] 잘못된 CSV/JSON이 구조화된 오류를 반환한다.
- [x] 같은 입력은 같은 변환 결과와 해시를 생성한다.
- [x] 버전 폴더의 중첩 CSV를 하나의 세션으로 변환한다.
- [x] 파일별 상대 경로, 해시와 레코드 수를 결과로 제공한다.
- [x] 큰 입력이 renderer를 차단하지 않는다.

## 7. Phase 2 - 검증 및 작업본

**상태: 진행 중**

### 목표

변환 결과를 공통 규칙과 도메인 규칙으로 검증하고, 원본과 분리된 작업본으로 관리한다.

### 범위

- 공통 validation 파이프라인
- 도메인별 validator 등록 구조
- 오류와 경고 모델
- 레코드 및 필드 위치 표시
- 정규화 전후 값 비교
- 경고 확인과 예외 사유 기록
- publish 가능 상태 계산

### 관련 요구사항

- `VAL-001` ~ `VAL-007`
- `OWN-001`, `OWN-004`
- `LOG-001`, `LOG-002`

### 종료 조건

- [ ] 공통 오류와 도메인 오류가 동일한 결과 계약으로 표시된다.
- [ ] 오류가 있는 작업본은 다음 반영 단계로 이동할 수 없다.
- [ ] 경고 확인 여부와 사유를 저장할 수 있다.
- [ ] 원본, 변환 결과, 작업본을 구분하여 조회할 수 있다.
- [ ] Jev 결과가 결정론적 validation을 대체하지 않는다.

## 8. Phase 3 - 버전 diff

**상태: 대기**

### 목표

두 버전의 데이터를 도메인별 안정 식별자로 비교하고 추가, 수정, 삭제를 검토한다.

### 범위

- 도메인별 identity 전략
- 추가, 수정, 삭제 계산
- 필드 단위 변경 결과
- 순서 변경과 값 변경 구분
- 검색, 필터, 정렬
- 변경 요약과 상세 UI

### 관련 요구사항

- `DIF-001` ~ `DIF-007`
- `VER-003` ~ `VER-005`

### 종료 조건

- [ ] 장비와 직업 fixture에서 추가, 수정, 삭제를 정확히 구분한다.
- [ ] 배열 순서만 바뀐 경우의 정책이 정의되어 있다.
- [ ] 필드 단위 이전 값과 이후 값을 표시한다.
- [ ] 현재 버전 변경 시 diff 결과가 새 컨텍스트로 갱신된다.
- [ ] 대량 diff 결과를 탐색할 수 있다.

## 9. Phase 4 - 도메인 편집

**상태: 대기**

### 목표

검증된 작업본에서 장비와 직업 데이터를 안전하게 추가, 수정, 삭제한다.

### 범위

- 장비 목록, 상세, 검색, 필터, 편집
- 잠재옵션 데이터 관리
- 직업 코드, 계열, 소속, 전직 단계 편집
- 참조 관계 검증
- 작업본 변경 이력
- 삭제 예약과 복원

### 관련 요구사항

- `EQP-001` ~ `EQP-007`
- `CLS-001` ~ `CLS-006`
- `SKL-001` ~ `SKL-003`

### 종료 조건

- [ ] 장비와 직업 CRUD가 작업본에서만 수행된다.
- [ ] 버전별 고유 제약과 참조 관계를 편집 전에 검증한다.
- [ ] 1.5차와 2.5차 전직 단계를 손실 없이 저장한다.
- [ ] 삭제된 항목을 publish 전 복원할 수 있다.
- [ ] 모든 편집이 diff 결과에 반영된다.

## 10. Phase 5 - DB dry-run 및 publish

**상태: 대기**

### 목표

승인된 작업본을 dry-run으로 검증하고 단일 버전 단위로 DB에 안전하게 반영한다.

### 범위

- dry-run 저장소 계층
- 예상 변경 건수와 오류 보고
- 사용자 승인 화면
- 버전 상태 전이
- 트랜잭션 publish
- 실패 롤백과 재시도
- 작업 로그

### 관련 요구사항

- `DB-001` ~ `DB-008`
- `SEC-003`, `SEC-004`
- `LOG-001` ~ `LOG-004`
- `VER-006` ~ `VER-009`

### 종료 조건

- [ ] dry-run은 DB를 변경하지 않는다.
- [ ] 승인 전 publish를 실행할 수 없다.
- [ ] 중간 실패 시 해당 publish의 변경이 모두 롤백된다.
- [ ] 성공한 버전만 ready로 전환된다.
- [ ] 실패 사유와 재시도 가능 여부를 확인할 수 있다.

## 11. Phase 6 - 타입 및 정적 데이터 생성

**상태: 대기**

### 목표

ready 버전을 기준으로 TypeScript 타입과 정적 데이터를 재현 가능하게 생성하고 검토한다.

### 범위

- generator 실행 계약
- 대상 버전과 출력 경로 표시
- 생성 순서 관리
- 실행 결과 요약
- Git diff 검토 연결
- 실패 상태 분리

### 관련 요구사항

- `GEN-001` ~ `GEN-006`
- `OWN-002`, `OWN-003`

### 종료 조건

- [ ] 같은 ready 버전에서 같은 생성 결과를 얻는다.
- [ ] DB 반영과 생성 실패를 서로 다른 상태로 표시한다.
- [ ] 생성 결과를 자동 커밋하지 않는다.
- [ ] 변경 파일과 오류를 사용자에게 요약한다.
- [ ] 패키지 빌드 순서를 지키며 전체 typecheck가 통과한다.

## 12. Phase 7 - 운영 안정화

**상태: 대기**

### 목표

반복적인 데이터 관리 작업을 안정적으로 수행할 수 있도록 복구, 이력, 성능과 배포를 보강한다.

### 범위

- 작업 이력 조회
- 취소 및 재시도
- 장애 복구 시나리오
- 대용량 목록 가상화
- 패키징 및 Windows 배포
- 로그 정책과 민감 정보 검사
- 핵심 흐름 end-to-end 테스트

### 관련 요구사항

- `LOG-001` ~ `LOG-005`
- `NFR-PERF-001` ~ `NFR-PERF-003`
- `NFR-REL-001` ~ `NFR-REL-003`
- `NFR-UX-001` ~ `NFR-UX-004`
- `NFR-COMP-001` ~ `NFR-COMP-003`
- `NFR-OBS-001` ~ `NFR-OBS-003`

### 종료 조건

- [ ] 실패한 작업을 원인 수정 후 재실행할 수 있다.
- [ ] 앱 재시작 후에도 작업 결과와 상태를 확인할 수 있다.
- [ ] 대표 데이터 묶음의 end-to-end 적재가 통과한다.
- [ ] renderer와 로그에서 비밀값이 검출되지 않는다.
- [ ] Windows 패키지가 설치 및 실행된다.

## 13. 보류 기능

초기 제품 완료 이후 검토한다.

- 폴더 및 다중 파일 일괄 선택
- 몬스터, 보스, 심볼 등 추가 도메인 편집 UI
- diff 보고서 내보내기
- 여러 관리자와 원격 협업
- 역할 기반 접근 제어
- 자동 업데이트
- 데이터 품질 통계와 Jev 평가 대시보드

Phase 0과 Phase 1은 완료됐다. 다음 구현 목표는 `GOAL.md`의 Phase 2
**검증 및 작업본 기반 구축**이다.
