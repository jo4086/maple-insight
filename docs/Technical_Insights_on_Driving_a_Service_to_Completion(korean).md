**maple insight** 프로젝트를 하게 되면서 개발의 흐름에 대해서 깨닫게 된 내용을 적어보자 한다.

**maple insight** 프로젝트는 유저가 온라인 게임의 닉네임을 검색하게 될 시 백엔드가 온라인 게임의 API를 받아온 데이터를 정제하여 프론트에 보내고 프론트는 그것을 보여주는 단순한 흐름을 가진다.

흐름은 단순할 지 몰라도 **게임 데이터** 특이성으로 인하여 여러가지 종류의 캐릭터 정보들을 분석하고 성장루트 및 전투의 시뮬레이션을 하게되므로 데이터의 범위부터 중요한 데이터들, 그리고 데이터를 어디까지 가공해야하는지 등에 대해서 처리 할 일이 많다는 것이다.

다루는 데이터의 종류와 수치가 많다보니 불필요한 정보들 또는 어떻게 로직을 짜야하는지 설계하기에는 방향성을 잡기 어려웠다.

그래서 먼저 가장 중요한 이 사이트가 UI가 존재한다면 사용자들에게 어떤것들을 제공할지 사용자들이 원하는게 무엇일지 구체화 하는게 좋다고 판단하여 프론트의 구조부터 설계하기 시작했다. (와이어 프레임 설계)

전체적인 레이아웃이라던지 이런게 있으면 좋겠다라는 막연한 느낌으로 구조가 완성되자 이제는 반대로 데이터에 따라서 UI가 따라가는 방향성으로 바뀌게 되었기에 백엔드의 정확한 설계가 필요해졌다.\

이제 백엔드의 설계를 다시 해야하는데 처음엔 방대한 데이터들과 가공의 방싱에 대해서 막막했던 부분이 프론트의 방향성 덕분에 필요한 데이터들과 필요치 않은 데이터들의 선별과 데이터들을 어떤 로직을 구상해서 가공할지에 대해서 가닥이 잡히게 될 것 같은 느낌이 들게 되었다.

이말은 불필요한 코드량을 줄이게 된다는 말이며 전체적인 생산성이 높아질 것이라 생각이 들었다.

그리고 1차적으로 백엔드의 구조가 잡히면 이제 이걸 바탕으로 프론트가 자세한 UI를 그리며 필요한 데이터와 불필요한 데이터, 부족한 데이터들을 구별하고 다시 백엔드에 수정사항을 피드백 한다.

이때 이미 프론트의 방향성을 알기 때문에 백엔드는 수정사항이 수월하게 될 것이며 버려지는 코드의 양도 줄어들게 되며 데이터의 보관방식, 캐싱, 통신방식에 대해서 추가적인 작업이 손쉽게 이루어 질 것이다.

이런 과정을 몇 번 반복하다보면 백엔드와 프론트는 서로의 구조를 파악하기에 소통이 수월하며 서로의 의도를 금방 알게될테니 백엔드와 프론트엔드라는 기술적 구분은 있을지라도 하나의 서비스에 대해 같이 개발하는 하나의 군체로써 작동하게 될 것 이며 이후 유지보수나 서비스의 업데이트가 있게 될 때도 진행이 수월 할 것 같다는 생각이 들었다.

즉 직무에 따른 구분이 서비스라는 더 큰 영역의 구분이 되어선 안된다는 생각이 들게 되었고

이를 통해 이상적인 팀의 구조에 대해서 고민하게 되었다.

**maple insight** 프로젝트를 진행하면서, 개발의 전체적인 흐름과 방향성에 대해 스스로 많은 것을 깨닫게 되었다. 이 문서는 그 과정을 정리한 기술적 통찰의 기록이다.

## 1. 프로젝트 개요

**maple insight** 는 온라인 게임의 유저 닉네임을 검색하면, 백엔드가 게임 API로부터 유저 데이터를 받아와 이를 정제해 프론트엔드에 전달하고, 프론트는 그 데이터를 시각화하여 보여주는 구조의 프로젝트이다.

구현 흐름 자체는 단순해 보일 수 있지만, 게임 데이터의 특이성으로 인해 다뤄야 할 정보가 복잡하고 방대하다.\
유저 캐릭터 정보의 분석, 성장 루트, 전투 시뮬레이션 등을 고려하다 보니 단순히 API 데이터를 전달하는 수준을 넘어 **어떤 데이터를 어떻게 다룰지**에 대한 고민이 필수적이었다.

## 2. 데이터에서 시작하지 않았다

처음에는 **막대한 양의 데이터와 복잡한 가공 방식**에 압도되어 백엔드 로직을 어떻게 구성해야 할지 방향을 잡기 어려웠다.\
그래서 먼저, 사용자 입장에서 이 서비스가 **어떤 경험을 줄 수 있을지**를 고민했고, 이를 바탕으로 프론트엔드의 구조부터 설계하기 시작했다.\
즉, **와이어프레임을 먼저 그리며 사용자 중심의 시나리오를 구체화**했다.

이러한 프론트 중심의 접근은 결국 데이터를 주도하는 것이 아니라, **데이터가 UI에 종속되는 흐름을 만들어냈다.**\
그 결과, 백엔드에는 보다 정확하고 명확한 설계가 필요해졌다.

## 3. 프론트가 백엔드의 방향을 제시하다

프론트의 구조가 구체화되자, 자연스럽게 어떤 데이터가 **정말로 필요한지**, 어떤 데이터는 **불필요한지**가 보이기 시작했다.\
이 덕분에 백엔드는 처음보다 훨씬 더 정제된 기준으로 로직을 설계할 수 있었고, 불필요한 가공 로직이나 중복된 데이터 처리 없이 효율적인 흐름을 구성할 수 있게 되었다.

이는 **불필요한 코드의 감소**로 이어졌고, 결과적으로 **전체 개발 생산성이 높아지는 계기**가 되었다.

## 4. 피드백 루프의 시작

1차적인 백엔드 설계가 완료되면, 프론트는 이를 기반으로 상세 UI를 그려내고, 부족하거나 누락된 데이터를 확인한 뒤 **백엔드에 수정 피드백을 전달**하게 된다.

이 시점에서는 이미 프론트의 방향성이 명확하기 때문에 백엔드 측에서도 수정이 훨씬 수월해지고, 버려지는 코드도 줄어들며 **데이터 보관 방식, 캐싱 전략, 통신 방식 등에 대한 후속 설계도 자연스럽게 이루어진다.**

## 5. 하나의 군체로 작동하는 개발팀

이 과정을 몇 번 반복하다 보면, 프론트와 백엔드는 서로의 구조와 의도를 이해하게 되고 **기술적 분리는 존재하지만 서비스 단위에서는 하나의 팀으로 작동**하게 된다.

이런 구조에서는 유지보수나 기능 업데이트가 필요할 때에도
소통이 원활하고 빠른 대응이 가능해진다.
