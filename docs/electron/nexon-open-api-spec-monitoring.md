# 넥슨 Open API 명세 변경 감지

- 요구사항 ID: `REQ001` (Electron)
- 작성일: 2026-11-02
- 상태: 설계안 · 미구현
- 담당 앱: `apps/electron`
- 대상: [메이플스토리 NEXON Open API 공식 문서](https://openapi.nexon.com/ko/game/maplestory/?id=14)와 [`packages/api-types`](../../packages/api-types/README.md)

## 목적과 역할

Electron 관리 앱을 실행했을 때 넥슨 공식 API 문서의 새 엔드포인트나 기존 명세 변경을 발견하고, 관리자가 앱 안에서 그 내용을 확인할 수 있게 한다. 관리자는 변경을 검토한 뒤 `api-types` 및 사용처에 어떻게 반영할지 결정한다. 이 기능의 책임은 **감지, 비교, 알림, 검토 상태 관리**이며, 타입 파일을 자동 수정하거나 DB에 복제하지 않는다.

현재 [`api-types/character/src/ability`](../../packages/api-types/character/src/ability/index.ts)는 엔드포인트와 파라미터 목록을 `contract.ts`, 요청 타입을 `params.ts`, 원본 응답 타입을 `raw.ts`, 공개 export를 `index.ts`에 나누어 둔다. 이 구조를 첫 비교 사례로 사용한다. 앱의 기존 Playwright 스크립트는 앱 화면 검증용이며, 공식 문서 수집 기능은 아직 없다.

## 작동 방식

1. **실행:** 앱 시작 후 비동기로 확인을 시작한다. 사용자가 원할 때 다시 확인할 수 있다. 앱을 실행하지 않은 동안에는 이 방식만으로 변경을 감지할 수 없음을 UI에 마지막 성공 시각으로 드러낸다.
2. **발견:** 공식 메이플스토리 문서의 사이드바에서 카테고리를 찾고, 각 카테고리의 엔드포인트 아코디언을 탐색한다. 현재 보이는 `?id=` 값 목록만을 영구적인 전체 목록으로 가정하지 않는다.
3. **수집:** 아코디언을 열어 메서드·경로, 파라미터, 응답 스키마를 읽는다. 먼저 클릭 과정에서 구조화된 명세 응답이 제공되는지 확인하고, 없다면 Playwright로 렌더링된 내용을 추출한다. 수집 원본의 URL과 시각을 기록한다.
4. **정규화와 검증:** 화면 표시 순서·공백 등 의미 없는 차이를 제거하고 엔드포인트별 명세로 정리한다. 필드명, 타입, 필수 여부, 중첩 구조, 배열, `null` 허용 여부를 **문서가 명시한 범위에서만** 기록한다. 알 수 없는 값은 추정하지 않고 `불확실`로 표시한다. 일부 항목을 읽지 못한 실행은 완전한 성공으로 취급하지 않는다.
5. **비교:** 최신 수집 결과를 마지막으로 검토한 공식 명세와 비교하고, 엔드포인트 경로를 기준으로 해당 `api-types`의 `contract.ts`·`params.ts`·`raw.ts`를 찾아 차이를 분류한다. 최초 실행에는 이전 공식 명세가 없으므로 현행 문서와 타입의 차이를 초기 점검 결과로 표시한다. 신규 엔드포인트라면 `index.ts`, 패키지 최상위 export, 빌드 및 package export 등록 필요성도 알린다.
6. **알림과 검토:** 변경 목록에서 공식 문서 링크, 이전·최신 명세, 현재 타입 표현, 변경 종류를 함께 보여준다. 관리자는 항목을 `확인함`으로 표시하거나 별도 코드 변경과 검증 후 `반영 완료`, 의도적으로 적용하지 않기로 했다면 사유를 남겨 `조치 불필요`로 표시한다. 확인 여부와 최종 처리 여부는 각각 유지한다.

## 책임 경계와 데이터 보관

| 영역 | 책임 |
| --- | --- |
| Electron Main 및 수집 작업 | 외부 문서 조회, 추출, 정규화, 비교, 로컬 상태 저장, 오류 처리. Playwright가 필요하면 Renderer 밖의 격리된 작업에서 실행한다. |
| Preload·Renderer | 제한된 IPC로 결과를 받아 알림·차이·상태를 표시하고, 사용자의 확인 동작을 전달한다. Renderer가 직접 외부 사이트나 파일 시스템에 접근하지 않는다. |
| `packages/api-types` | 사람이 검토해 수정하는 원본 타입 계약. Git 이력을 변경 기록으로 사용한다. |
| 로컬 관리 상태 | 마지막으로 검토한 공식 명세 스냅샷, 변경 식별 해시, 확인·반영 상태, 마지막 성공·실패 시각만 보관한다. 전체 타입 소스를 DB에 복제하지 않는다. |

앱이 두 PC 이상에서 같은 검토 상태를 공유해야 한다면 로컬 상태 대신 공용 저장소가 필요하다. 이 요구가 확인되기 전에는 기존 게임 데이터 DB에 공식 문서 스냅샷을 섞지 않는다. 수집 결과가 달라졌다는 이유만으로 기준 스냅샷을 자동 갱신하면 미검토 변경이 사라질 수 있으므로, 최신 관측 결과와 검토 기준을 분리한다. 최초 점검의 기준 확정 및 이후 변경의 기준 반영은 관리자가 해당 결과를 최종 처리할 때만 수행한다.

## 변경 분류와 안전 기준

- 엔드포인트 추가·삭제, 파라미터 추가·삭제·필수 여부 변경, 응답 필드 추가·삭제, 타입·배열·중첩·`null` 허용 여부 변경을 별도 항목으로 보여준다.
- 공식 문서의 예시 응답과 스키마 설명이 다르거나 추출 결과가 불명확하면 자동 결론을 내리지 않고 검토 필요로 표시한다.
- 기존 타입을 사용하는 백엔드 매퍼 등은 변경 영향 대상으로 안내하되, 이 기능이 그 코드를 자동 변경하지 않는다.
- 중복 알림은 변경 내용의 안정적인 식별자로 묶는다. 이미 확인한 변경이 공식 문서에서 다시 바뀌면 새 변경으로 알려준다.
- 공식 페이지 구조가 바뀌거나 일부 아코디언이 누락되면 삭제된 API로 단정하지 않는다. 마지막으로 확인한 명세를 유지하고 수집 오류를 알린다.

## 구현 전 확인할 사항

1. 아코디언 클릭 후 Network에 기계가 읽을 수 있는 명세 응답이 있는지, 또는 DOM 추출이 필요한지 확인한다.
2. 개발 실행뿐 아니라 배포된 Electron 앱에서도 조회할지 결정한다. 현재 Playwright는 Electron의 개발 의존성이므로 배포 시 브라우저 실행 파일과 크기를 별도로 설계해야 한다.
3. 확인·반영 상태의 저장 위치와 다중 PC 공유 필요성을 결정한다.
4. 앱이 열린 동안의 재확인 주기와 알림 형태를 정한다. 시작 시 확인과 수동 재확인은 필수이고 주기 실행·운영체제 알림은 후속 결정이다.

## 검증 기준

- `character/ability`를 첫 사례로 실제 문서의 파라미터와 응답 스키마를 추출해 현재 네 파일과 비교한다.
- 신규 엔드포인트, 기존 필드 변경, 공식 문서의 일시적 접속 실패, 페이지 구조 변경을 각각 구분한다.
- 앱 시작 시 화면 사용 가능 여부, 중복 알림 방지, 재시작 후 미처리 상태 보존, 확인과 반영 완료의 차이를 확인한다.
- 감지 실행 전후 `api-types`와 Git 작업 트리가 바뀌지 않았음을 확인한다.

이 문서는 구현을 위한 제안 명세다. 현재 Electron ROADMAP의 Phase 완료 상태나 기존 REVIEW의 검증 결과를 변경하지 않는다.
